### 关键发现①：步骤16必须拆成两个节点

**原因**：LangGraph 有条硬规则——`interrupt()` 之前的代码，每次 resume 都会重新跑一遍。步骤16里"调用翻译服务"是有副作用的操作（真实网络调用），如果把它和"条件中断"写在同一个节点里，条件触发中断后每次 resume 都会重新调一次翻译 API，白白浪费调用次数。

**做法**：把步骤16拆成"翻译+检测"（无中断，只执行一次）和"人工校对"（只做 interrupt，天然幂等）两个节点。这是 LangGraph 官方文档明确推荐的模式（"Separate side effects into separate nodes"）。

```python
# nodes/step16_17.py
from langgraph.types import interrupt

# 以下三个函数假设第4周已实现
# call_translation_service(cn_subtitles) -> list
# detect_layout_anomalies(en_subtitles) -> list
# apply_human_layout_fix(en_subtitles, human_fix) -> list

def node_step16a_translate_and_check(state: VideoWorkflowState) -> dict:
    """副作用(调用翻译API)独立成节点,不含interrupt,只会执行一次"""
    translated = call_translation_service(state["cn_subtitles"])
    issues = detect_layout_anomalies(translated)
    return {
        "en_subtitles": translated,
        "layout_issues": issues,
        "layout_issues_detected": bool(issues),
    }

def route_after_translate(state: VideoWorkflowState) -> str:
    if state["layout_issues_detected"]:
        return "checkpoint3_layout_review"
    return "step17_inject_english_tts"

def node_checkpoint3_layout_review(state: VideoWorkflowState) -> dict:
    """只做interrupt,不做其它有副作用的事,天然幂等"""
    human_fix = interrupt({
        "checkpoint": "③",
        "step": 16,
        "ask": "英文字幕排版异常,请人工在剪映界面校对",
        "issues": state["layout_issues"],
    })
    return {"en_subtitles": apply_human_layout_fix(state["en_subtitles"], human_fix)}
```

### 关键发现②：关卡②和关卡③可能同时挂起，resume写法不一样

**原因**：关卡②在中文主线（步骤12），关卡③在英文分支（步骤16），两条分支并行跑。如果步骤16这次真的检测到排版异常，关卡②和关卡③会**同时**处于挂起状态。这时候用 `Command(resume="某个值")` 会直接报错：

```
RuntimeError: When there are multiple pending interrupts,
you must specify the interrupt id when resuming.
```

**正确写法**：把每个中断的 `id` 和对应的人工输入配成字典，一次性 resume。第2-3周单独测关卡①②时不会遇到这个问题（因为当时只有一条线），只有本周把两条分支接到一张图里同时跑，这个坑才会暴露——这正是"全流程端到端联调"要做的事。

```python
# checkpoint_resume.py
from langgraph.types import Command

async def resume_all_pending(graph, config, values_by_checkpoint: dict):
    """
    把当前所有挂起的中断,按checkpoint标识自动匹配并一次性resume。
    values_by_checkpoint 形如 {"②": "民谣风BGM.mp3", "③": "人工已校对完成"}
    只有1个中断挂起时,这个函数同样适用,不需要写两套逻辑。
    """
    snapshot = await graph.aget_state(config)
    resume_map = {}
    for i in snapshot.interrupts:
        cp = i.value.get("checkpoint")
        if cp in values_by_checkpoint:
            resume_map[i.id] = values_by_checkpoint[cp]
    if not resume_map:
        raise ValueError("没有匹配到待恢复的中断,检查values_by_checkpoint的key")
    return await graph.ainvoke(Command(resume=resume_map), config)
```

## 阶段二：人工关卡多日挂起模拟测试（Day 3）

### 目标

验证"进程完全退出几天后再启动"这个场景，而不是只测"同一进程里 interrupt 完立刻 resume"。

**设计要点**：不需要真的等3天。真正要测的是"全新进程重新连接同一个 checkpoint 文件/数据库后能否正确恢复"，这跟等多久无关。用文件型 SQLite（不能用 `:memory:`），退出 `async with` 块模拟进程关闭，重新进入模拟重启即可。

### 关键发现③：幂等判断不能用 state 字段，必须查真实产物

这是最容易踩的坑，实测复现了两种写法的真实差异：

```python
# 错误写法:用state里的标记位判断
def node_checkpoint1_bad(state):
    if not state.get("snapshot_saved"):
        save_draft_snapshot(...)             # 实测:resume后会再执行一次!
    order = interrupt({...})
    return {"shot_order": order, "snapshot_saved": True}
```

原因：`snapshot_saved` 这个标记位要等节点**正常 return** 才会被 checkpoint 记下来。但第一次执行时，代码在 return 之前就被 `interrupt()` 中断退出了，标记位根本没写进去。resume 重放时，state 里读到的还是初始值 `False`，判断完全失效。实测：这种写法副作用会执行 **2次**。

```python
# 正确写法:检查磁盘上的真实文件是否已存在
def node_checkpoint1_good(state):
    snapshot_path = f"{state['draft_dir']}/snapshot_before_review.json"
    if not os.path.exists(snapshot_path):    # 跨进程可见的真实证据,不是state字段
        save_draft_snapshot(state["draft_dir"], snapshot_path)
    order = interrupt({...})
    return {"shot_order": order}
```

实测：这种写法，无论 resume 几次，副作用都只执行 **1次**。

## 阶段三：状态结构变更兼容性演练（Day 3-4）

### 目标

验证"发新版本、State新增字段后，挂起中的旧线程恢复时不报错"。

### 关键发现④：新字段不给默认值，resume会直接KeyError

实测复现：

```python
# 第2周定义的State(节选)
class VideoWorkflowStateV1(TypedDict):
    video_name: str
    shot_order: list

# 假设第5周新增字段:heartbeat_id(关联第3周心跳监控)
class VideoWorkflowStateV2(TypedDict):
    video_name: str
    shot_order: list
    heartbeat_id: str          # 新增字段

# 错误写法:直接按key取值
def node_bad(state: VideoWorkflowStateV2):
    hb = state["heartbeat_id"]     # 实测:resume一个"加字段前"的旧checkpoint时
    ...                              # 直接抛出 KeyError: 'heartbeat_id'

# 正确写法:.get()给默认值,对应文档5.2节"新字段给默认值"的规范
def node_good(state: VideoWorkflowStateV2):
    hb = state.get("heartbeat_id", generate_heartbeat_id())
    ...
```

这条实测把文档里"只加字段、不删字段、新字段给默认值"这条规范，变成了一条可以在CI里跑的断言。

### 破坏性变更应急预案：自建运行台账

文档5.2节坑⑤提到，真要做破坏性变更时，得先查出所有挂起中的线程。与其去扒 LangGraph checkpointer 内部表结构（不同版本可能变），不如自己建一张轻量台账表，专门维护"哪些线程正挂起在哪个关卡"：

```sql
-- 运行台账表(与Postgres checkpointer共用同一个库)
CREATE TABLE IF NOT EXISTS workflow_runs (
    thread_id TEXT PRIMARY KEY,
    video_name TEXT NOT NULL,
    current_checkpoint TEXT,          -- '①'/'②'/'③'/NULL(未挂起)
    status TEXT NOT NULL,              -- 'running'/'suspended'/'completed'/'failed'
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

```python
async def mark_suspended(conn, thread_id, video_name, checkpoint):
    await conn.execute(
        """
        INSERT INTO workflow_runs (thread_id, video_name, current_checkpoint, status)
        VALUES (%s, %s, %s, 'suspended')
        ON CONFLICT (thread_id) DO UPDATE
        SET current_checkpoint = EXCLUDED.current_checkpoint,
            status = 'suspended', updated_at = CURRENT_TIMESTAMP
        """,
        (thread_id, video_name, checkpoint),
    )

# 发版前运维查询:一条SQL就知道要不要处理
# SELECT thread_id, video_name, current_checkpoint FROM workflow_runs WHERE status = 'suspended';
```

在每个关卡节点的 `interrupt()` 调用前后，各调一次 `mark_suspended` / 状态更新，就能维护起来（放哪个位置调用，同样要遵守"幂等/挪到独立节点"的原则）。

### 关键发现⑤：SQLite自动建表，Postgres不会

这是切换时最容易漏掉的一步——查源码确认过：

| Checkpointer | 首次使用建表方式 |
|---|---|
| `AsyncSqliteSaver` | **自动**建表，源码原话："called automatically when needed and should not be called directly" |
| `AsyncPostgresSaver` | **必须手动**调 `.setup()`，源码原话："MUST be called directly by the user the first time" |

开发时用SQLite一直"能跑"，切到Postgres后如果漏了 `.setup()`，第一次运行会报表不存在的错误。

### 切换代码

```python
# checkpointer_factory.py
import os
from contextlib import asynccontextmanager
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

@asynccontextmanager
async def get_checkpointer():
    """统一入口:按环境变量选开发(SQLite)还是生产(Postgres)"""
    env = os.environ.get("WORKFLOW_ENV", "dev")

    if env == "production":
        db_uri = os.environ["POSTGRES_URI"]
        # 例:postgresql://video_workflow:密码@localhost:5432/video_workflow
        async with AsyncPostgresSaver.from_conn_string(db_uri) as checkpointer:
            await checkpointer.setup()   # 必须手动调,见"关键发现⑤"
            yield checkpointer
    else:
        db_path = os.environ.get("SQLITE_DB_PATH", "dev_checkpoint.db")
        async with AsyncSqliteSaver.from_conn_string(db_path) as checkpointer:
            yield checkpointer           # SQLite会自动建表,不需要手动调


# 使用方式(main.py里统一这样启动)
async def main():
    async with get_checkpointer() as checkpointer:
        graph = build_graph(checkpointer)
        # ... 后续逻辑不变,graph本身不关心底层是SQLite还是Postgres
```

`POSTGRES_URI` 建议放环境变量，不要写死在代码里（密码明文进git风险）。
