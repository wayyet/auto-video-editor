# 执行记录:创建台「继续运行」按钮与失败节点重试(2026-11-17)

## 背景与需求

操作员在创建台页面(console.html)「创建并运行工作流」按钮旁的红圈空位处需要一个按钮,点击后继续运行当前工作流:

1. 停在人工关卡(waiting_human,关卡①分镜顺序/关卡②BGM 确认)→ 继续运行;
2. 节点报错(run.failed)→ 重试该节点。

## 现状核实(实施前探索结论)

- **关卡恢复链路前后端已全齐**:`POST /api/console/runs/{tid}/resume`(api_console.py:548)→ `console_service.resume_run`(console_service.py:694)→ 子进程 `scripts/resume_workflow.py` 注入 `Command(resume=...)`;创建台已有恢复面板(`showResumePanel`,waiting_human 时自动弹出)。**零后端改动**。
- **failed 重试此前明确不支持**(双重拦截):API 层非 waiting_human 一律 409(console_service.py 原 740-745);CLI 无挂起关卡即退出码 4(resume_workflow.py 原 325-330)。
- **LangGraph 能力已在仓库内验证**:`run_with_events(g, None, config)`(None 输入)从最后 checkpoint 续跑,失败 superstep 写入未提交 → 失败节点重新执行(`monitoring/workflow_runner.py:508` 已把 None 输入按 resume 处理发 `run.resumed`;`agent_gate/runner.py:612` 的 `continue_after_crash` 模式即先例;`tests/integration/test_workflow_stream_events.py:453-464` 锁定该语义)。缺口只是入口 A 恢复管线未暴露。

## 交互决策(操作员拍板)

| 场景 | 行为 |
|---|---|
| waiting_human | 点按钮 → **弹出现有恢复面板**(显示挂起关卡内容/QC 警告/草稿入口),人工点「确认恢复」才放行 |
| failed | 点按钮 → **先弹 confirm 确认框**(真实重跑会消耗 LLM 调用与时间),确认后提交重试 |

按钮文案随状态切换:waiting_human=「继续运行」,failed=「重试失败节点」。

## 真机 E2E 验收清单(待操作员,需管理员 pwsh7 重启服务生效)

1. 新建任务跑到关卡① → 创建台出现「继续运行」按钮 → 点击弹出恢复面板(含关卡卡/QC 警告)→ 确认恢复 → SSE 事件续跑。
2. 造/找一个 failed 任务 → 创建台出现「重试失败节点」→ 点击弹 confirm → 确认后 202 → 事件流出现 `run.resumed` + 失败节点重新 `node.started` → 最终到终态。
3. failed 任务在剪映未关闭时重试 → 409「恢复前检查未通过」(有草稿场景)。
4. completed/prepared/运行中任务 → 按钮隐藏;查看模式(`?thread_id=`)下按钮可用。
5. 失败发生在产草稿前(无草稿)的重试 → 不要求关剪映,直接续跑。

## 边界与语义说明

- **cancelled 不放行**:操作员主动取消的任务不在本按钮能力内(保持终态语义),只能新建任务。
- **checkpoint 缺失/PG 不可达 fail-closed**:服务层 202 后由子进程校验,失败以退出码 7 落 `console_run.log`;事件库不会有 `run.resumed`,前端停在 failed 态可重试。
- **重试语义 = 重跑失败节点**:LangGraph 从最后提交的 checkpoint 续跑,失败 superstep 的写入未提交;不是"从任务最开始重跑"。
