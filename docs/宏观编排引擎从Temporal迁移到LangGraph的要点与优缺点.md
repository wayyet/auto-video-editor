# 宏观编排引擎选型：从 Temporal 换成 LangGraph，要注意什么？

## 这篇文档在讲什么

RFC 原方案里，"宏观编排引擎"（管着整条视频剪辑流水线从头跑到尾的那个"总调度"）选的是 Temporal，LangGraph 只负责流水线里某几步"AI 自己琢磨该干嘛"的小循环。这篇文档讨论的问题是：**如果把"总调度"这个角色也换成 LangGraph，会发生什么。**

结论先说：技术上能跑通，但跑通的代价，大部分花在"把 Temporal 本来就自带的能力，在 LangGraph 里重新搭一遍"，而不是换了个更合适的工具。

## 先搞懂这两个框架分别"擅长什么"

打个比方：

- **Temporal 像一个不知疲倦、记性超好的工厂调度员。** 不管一个订单要经过几十道工序、中间要等审批等多久，它都能准确记住进度；也能把不同性质的活分给不同班组干（比如这道工序必须 A 车间做，那道工序必须 B 车间做）。
- **LangGraph 像一个特别擅长主持"AI 讨论会"的主持人。** 组织模型一步步推理、决定下一步该调用哪个工具、该找谁帮忙，脑力活是它的强项。但"这个活必须在哪台机器上干""干活的人换班了怎么办"这种运营细节，本来不是它设计时要解决的问题——虽然这一年它也在往这个方向补课。

这条视频剪辑流水线的特点是：大部分步骤是"正常业务流程 + 桌面软件自动化"，AI 推理只占其中几步。这也是为什么原 RFC 让 Temporal 当"总调度"、LangGraph 当"讨论会主持人"，而不是反过来。

## 换成 LangGraph 当总调度，要留意的 5 个坑

**1. Windows/Linux 分工，没有现成的"排班表"**

剪映的自动化工具在 Windows 上功能齐全，在 Linux 上阉割了导出功能。Temporal 有个叫 Task Queue 的机制，天生就能把某道工序精准派给"Windows 班组"或"Linux 班组"。LangGraph 默认整张图在一个运行时里跑，没有这种"排班"概念，得自己搭一层消息队列去往 Windows 机器派活、等结果回来。

**2. .NET 那部分代码，接不进 LangGraph 的图里**

如果 Windows 侧的控件自动化用 .NET 写（比如 FlaUI 这类库），Temporal 下这就是很自然的"再起一个 .NET worker，接到专属任务队列上"。换成 LangGraph 就不行了——它官方只支持 Python（和实验性的 JS），没有 .NET SDK。.NET 那部分只能包装成一个独立服务，让 Python 这边的节点跨进程调过去，多一层要单独维护的服务。

**3. 人工审核关卡（比如等人工挑背景音乐，可能要等好几天）能挂起，但恢复时有个隐藏坑**

两边现在都能做到"挂起等着、不占算力"，这点已经打平了。但 LangGraph 有个容易踩的细节：流程恢复执行时，等审批那个节点里、"喊暂停"那行代码**之前**的逻辑，会被重新跑一遍（更早的节点不会重跑）。如果这个节点在喊暂停之前顺手做了点有副作用的事（比如先给草稿存个快照、先发个通知），这段逻辑就得自己保证"重复执行也没事"，不然每次恢复都可能把这件事再干一遍。Temporal 那边因为每一步做完就记一笔账，重放时不会重复执行已经做完的步骤，心智负担相对小。

**4. "卡住了"和"死机了"，现在分辨起来没那么容易**

Temporal 有个"心跳"机制：干活的一方要定期"打卡"，服务端据此能独立判断"是这活儿本来就慢，还是干活的那台机器已经失联了"——这个判断跟具体哪个进程存活没关系。LangGraph 现在也有超时机制（一个管总时长、一个管"是不是还有动静"），能力已经不弱，但运作的前提是这次节点执行的进程还在。如果跑 GUI 自动化的整台 Windows 机器直接掉线，这类"机器没了"的更底层故障，还是得自己另外接监控才能发现。

**5. 流程卡在人工关卡时，团队发新版本会不会炸**

这条要分两半看：

- 如果只是调整流程本身（加个步骤、改个分支），LangGraph 现在处理得还不错，卡住的流程大概率不受影响。
- 但如果动了"状态"本身的字段结构（比如给状态加了个必填字段），LangGraph 没有自动迁移这回事——卡在人工关卡好几天的那些流程，等恢复的时候直接读取报错，而且报错信息跟"字段改了"这件事不一定能对上号，排查起来费劲。Temporal 有专门的官方 API 来处理"流程跑到一半、代码却发新版本了"这种场景，LangGraph 这边目前只能靠团队自己约定"只加字段、不删字段、新字段给默认值"来兜底。

## 优缺点一览

| 维度 | Temporal | 换成 LangGraph 后 |
|---|---|---|
| Windows/Linux 派工 | 自带排班机制 | 要自己搭一套 |
| 接入 .NET 代码 | 官方支持，直接接 | 无官方 SDK，得包一层服务 |
| 人工关卡挂起 | 恢复不重复做已完成的事 | 可以挂起，但节点内前置逻辑要自己保证不重复出问题 |
| 机器失联怎么发现 | 心跳机制，与进程存活状态解耦 | 有超时机制，但主要管当次执行内部 |
| 卡着的流程赶上发新版本 | 有官方版本兼容 API | 流程结构改动兼容尚可，数据结构改动没有自动迁移 |
| 要额外运维的东西 | 一整套 Server + 数据库 | 基本就是装个 Python 包 |
| "AI 这步为什么这么判断"好不好查 | 一般，偏输入输出和耗时 | 好，自带的追踪工具对这块很擅长 |

## 优点

- **少养一套系统。** Temporal 要单独部署 Server、数据库，运维成本是实打实的；LangGraph 基本就是加一个 Python 依赖，起步轻很多。
- **技术栈统一。** 如果流水线里"AI 决策"那几步本来就打算用 LangGraph，宏观编排也用同一套，团队少学、少维护一样东西。
- **审计"AI 为什么这么决定"更方便。** LangGraph 自带的追踪工具，在这件事上天然比 Temporal 好用。
- **以后如果分支逻辑越来越依赖模型自己判断**（而不是现在这种"走不走 GUI、走哪个系统"式的确定性规则），LangGraph 的写法会更顺手。

## 缺点

- 上面列的 Windows/Linux 派工、接 .NET、发版兼容这几件事，Temporal 都是现成的，换 LangGraph 基本都要自己重新搭。
- 说到底，这条流水线的本质是"业务流程 + 桌面自动化"，AI 只是其中几步。用一个专为"AI 一步步推理"设计的框架去装这种活，天然有点别扭——这一点即使 LangGraph 这一年功能补了不少，也没有从根子上变。

## 结论 / 建议

不是说这么做技术上跑不通，而是跑通所花的力气，大部分都是在把 Temporal 已经内置好的东西，在 LangGraph 里重新搭一遍。如果动机是团队更熟悉 LangGraph、暂时不想背 Temporal 的运维成本，比"整条流水线都交给 LangGraph"更稳的做法，是延续 RFC 原本的分工思路：**LangGraph 负责不需要长时间挂起、不用跨 Windows/Linux 调度的那一段（比如纯 AI 决策的几步），真正要扛"挂起好几天"和"双系统调度"的部分，还是交给 Temporal。**
