## 3. 故障链路还原与正确性核验

### 3.1 调用链

按附件的本机日志记录，调用路径为：

```text
node_16a_translate_and_check
  └─ translate_segments(segments_zh)
      └─ LLMTranslateClient._translate_batch()
          └─ LLMTranslateClient._call_llm()
              └─ storyline_capabilities.vlm_client.chat_json_with_trace()
                  └─ McodeCLIClient.chat()
                      └─ mcode exec --mode lightweight --output-schema <临时文件>
                          └─ 模型服务
```

代码核验结果：

1. `node_16a_translate_and_check` 调用 `translate_segments()`，翻译结果校验失败后会收到 `TranslationError`。
2. `LLMTranslateClient` 默认 `TRANSLATION_MAX_RETRIES = 1`，因此外层最多调用两轮。
3. `McodeCLIClient` 继承 `_CLIClient`，父类默认 `max_attempts = 2`；每次 `chat()` 最多进行两次 CLI 尝试。
4. 在默认配置未被覆盖的前提下，最多为两轮外层调用 × 两轮 CLI 内部尝试，即四次 CLI 执行。

因此附件中“共 4 次 mcode 调用”的计算与当前默认代码一致。该数字依赖 `max_attempts=2` 未被运行时配置覆盖，正式记录应保留这一前提。

### 3.2 输出契约

当前 `jy_common/translate_client.py` 的目标输出结构为：

```json
{
  "translations": [
    {"index": 0, "text_en": "Hello there"},
    {"index": 1, "text_en": "See you tomorrow"}
  ]
}
```

模型输出必须满足：

- 顶层对象必须包含 `translations` 数组；
- 数组元素必须为对象，不得为纯字符串；
- 每个元素必须包含整数 `index` 和非空字符串 `text_en`；
- `index` 集合必须与输入批次完全一致，不得缺失、重复或多出；
- 时间码由源字幕段继承，不采信模型自行生成的时间字段。

`_validate_and_merge()` 实现了上述主要约束，并按源段 index 重组结果。时间码由源数据继承，这一点也有单测覆盖。

附件列出的四类错误输出（顶层误用 `segments`、元素字段误用 `text`、元素退化为字符串、段数或 index 变化）与该输出契约不兼容，作为失败原因是合理的。

### 3.3 Prompt 与 schema 的关系：需要精确描述

代码可直接确认：

- `_SYSTEM_PROMPT` 已包含完整 JSON 输出示例；
- `McodeCLIClient` 在 `lightweight=True` 时通过 `compose_prompt()` 把 system prompt 合并到用户任务文本中；
- schema 通过 `--output-schema` 参数传给 mcode CLI；
- `--output-schema` 不会被本仓库代码拼接进普通 prompt 文本。

但“schema 只在模型生成后才校验、模型内部完全不可见”这一点，不能仅从仓库代码完全证明。附件提到的模型 thinking 和本地 session transcript 是该判断的重要证据，但这些 `.minimax` 会话文件没有随附件提供，无法在本次审查中独立读取。建议把文档措辞调整为：

> 本次事故的模型会话记录显示，模型没有按预期理解 `--output-schema` 的目标结构；仓库代码可见的普通任务 prompt 原先也没有提供目标 JSON 示例。为消除模型对输出形状的推断空间，修复将目标结构直接写入 prompt，并保留 schema/代码校验作为第二道约束。

这样既保留了事故证据，也不会把“CLI 将 schema 如何传递给模型内部”说成仓库代码已证明的事实。

### 3.4 真实错误为何变成“缺少 translations 数组”

`chat_json_with_trace()` 会捕获 `client.chat()` 抛出的异常，并返回空对象 `{}` 与 trace；随后翻译客户端继续执行 `_validate_and_merge()`。当校验对象是 `{}` 时，最终看到的错误自然是“缺少 translations 数组”。

因此附件指出“表面错误是对空 dict 的判断，不一定是模型原始文本直接缺少 translations”的结论是成立的。

但应区分两种情况：

- **CLI 正常返回文本**：`chat_json_with_trace()` 可以把返回文本写入 `trace.raw_head`，之后再解析 JSON。
- **CLI 内部重试耗尽并抛异常**：`chat_json_with_trace()` 捕获异常时没有拿到 `client.chat()` 的原始返回文本，当前实现只记录异常 `repr` 到 `trace.error`，`trace.raw_head` 保持空字符串。

附件描述的故障路径包括 CLI 适配器内部重试后抛出 `CLIBackendInvalid`。在这条路径上，新增加的 diagnostics 文件**不保证包含模型原始输出**。这是本次审查发现的实质性缺口，详见第 5.1 节。

## 4. 已实施修复审查

### 4.1 Prompt v1 升级 v2

当前代码已将：

```python
TRANSLATION_PROMPT_VERSION = "subtitle-translate-v2"
```

并在 `_SYSTEM_PROMPT` 中加入完整的 `translations` 结构示例，以及对顶层键、数组元素类型、字段名和 index 的约束。

**评价：通过。** 这是本次故障最直接、最小化的修复，不改变翻译输出契约，也不放宽下游校验。

建议保留“提示词变更必须升级版本号”的约定。后续修改 prompt 时应同步修改 prompt 守卫测试，避免只更新文字而忘记 marker 版本。

### 4.2 严格输出校验与 fail-closed

当前 `_validate_and_merge()` 不接受错误结构；node_16a 在捕获 `TranslationError` 后先执行 best-effort 诊断写盘，再原样 `raise`。只有翻译成功后才执行草稿写入、marker 保存和 SRT 写入。

**评价：通过。** 不建议加入 `segments`、`text` 等候选键自动转换，也不建议把纯字符串数组强制包装成对象。此类容错会掩盖模型输出契约漂移，并增加 index 对齐错误风险。

### 4.3 Marker 版本及缓存失效

`nodes/node_16_translate_subtitles.py` 的 `_compute_source_fingerprint()` 将 `prompt_version` 纳入 SHA-256 指纹；`_marker_exists()` 还会分别检查 marker 内的 `prompt_version`、`translator_id`、源指纹和段数。

**评价：通过。** v2 上线后，旧 v1 marker 不会被误当成当前 prompt 的翻译结果。已成功翻译的存量草稿下一次运行需要重新翻译一次，是预期缓存失效成本，不是幂等性退化。

### 4.4 node_16a 诊断落盘

当前节点会在 `TranslationError` 上抛前，尝试把以下字段写入：

```text
<storyline_outputs_root>/diagnostics/translation-failure-<UTC时间戳>.json
```

包括 node 名、translator_id、prompt_version、段数、fingerprint 和 `exc.trace`。缺少输出目录或写盘异常均不会覆盖原始翻译异常，符合 best-effort 的定位。

**评价：部分通过。** 文件路径、字段和 fail-safe 处理已实现；但当前 trace 捕获边界未覆盖 mcode CLI 内部异常重试中的原始输出，不能将 diagnostics 功能描述为“已经完整保存所有模型尝试”。

### 4.5 共享客户端对 node_15 的影响

当前 `node_15_localize_covers_en.py` 通过默认翻译客户端调用 `client.translate()`，因此与 node_16a 共享 `LLMTranslateClient` 的 prompt、schema 和输出校验逻辑。

**评价：附件描述基本准确。** node_15 的真机输出能够验证共享翻译客户端的 prompt 对至少一个单段输入有效；但它不能证明 node_16a 的多段字幕、marker、SRT 和下游英文字幕节点已在真实 mcode 环境完整通过。

## 5. 文档与实现存在的问题

### 5.1 P1：CLI 内部失败时，diagnostics 的 `raw_head` 可能为空

**问题位置：**

- `agent_gate/cli_client.py`：`_CLIClient.chat()` 内部执行 `max_attempts` 次尝试，结束后可能抛出 `CLIBackendInvalid`；
- `storyline_capabilities/vlm_client.py`：`chat_json_with_trace()` 捕获 `client.chat()` 异常后，设置 `trace.error` 并返回 `{}`；异常分支没有把 CLI 内部每次拿到的模型输出带回 `raw_head`；
- `nodes/node_16a_translate_and_check.py`：只将收到的 `exc.trace` 写入 diagnostics。

**影响：** 附件中的生产故障恰好描述了“CLI 内部重试耗尽 → `CLIBackendInvalid` → `chat_json_with_trace` 捕获异常”的路径。按当前实现，该路径可能只落盘异常摘要，无法从新增 JSON 文件直接看到四次模型原始输出。

现有 `test_node_16a_translation_failure_fails_closed` 使用的 `_BadLLM.chat()` 是直接返回 `not-json-at-all`，因此 `chat_json_with_trace()` 能够填充 `raw_head`。这个测试证明了“LLM 正常返回非法文本时可留痕”，**没有证明 mcode CLI 内部重试抛异常时也能留痕**。

**修复建议：**

1. 在 CLI 适配器内部保留有限长度的逐次尝试摘要，例如 attempt 序号、CLI 状态、结构化校验错误、原始输出摘要（截断后）；
2. 在 `CLIBackendInvalid` 或一个专用异常对象上携带该摘要，不要只拼接一段不可解析的异常字符串；
3. 让 `chat_json_with_trace()` 在异常分支把可用的结构化诊断数据写入 trace；
4. 保持密钥、环境变量、完整命令行参数不进入日志；原始模型响应应设长度上限；
5. 增加一个模拟 `McodeCLIClient` 内部两次结构校验失败的测试，断言外层 `TranslationError.trace` 和 diagnostics JSON 中包含两次 CLI 尝试摘要。

这属于**窄范围诊断增强**，不要求重构全局 runner，也不需要改变 fail-closed 语义。

### 5.2 P1：node_16a 的真实字幕翻译分支没有完成真机验收

附件的真机验证记录显示：

- node_15 封面标题翻译使用共享 `LLMTranslateClient`，mcode 首次返回正确的 `translations` 结构；
- node_16a 的事件状态为 succeeded，但实际原因是 `video-001` 没有中文字幕，节点走 `STATUS_SKIPPED`；
- 因为没有源字幕，node_16a 没有调用真实字幕翻译，也不会生成英文字幕 SRT。

**影响：** 当前证据可以支持“共享 prompt 已在 node_15 的单段翻译请求中得到一次真实模型正确响应”，但不能支持“node_16a 的真实字幕翻译链路已真机验收通过”。

**修复/验收建议：** 选择一个确实具有 `subtitle_segments_zh` 的有效样本，确保 `draft_dir_en_branch` 指向可写的英文分支草稿，并通过真实 mcode CLI 执行 node_16a。验收时必须确认：

- node_16a 没有走 `skipped_no_source_subtitles`；
- `subtitle_translation_status == "real"`；
- 输出段数和输入一致，index 集合完全一致；
- 每段 `text_en` 非空；
- `subtitle_en.json` marker 为 schema v2，`prompt_version` 为 `subtitle-translate-v2`；
- `subtitle_en.srt` 已实际生成且时间码继承源字幕；
- 下游 `node_08b_add_subtitles_en` 能读取并使用英文结果；
- 对同一输入 resume 时 marker 命中，不重复调用模型。

### 5.3 P2：新增测试没有直接覆盖事故中的全部四种错误形状

当前测试有 prompt 示例守卫、非法 JSON、缺失 `text_en`、index 缺失/重复/多余和空译文等覆盖，但新增 prompt 守卫主要检查字符串是否存在；没有看到对事故中四种原始响应形状逐一参数化的回归测试。

**建议补充：**

| 输入模型输出 | 预期行为 |
|---|---|
| `{"segments": [...]}` | 校验失败并重试，重试耗尽后抛 `TranslationError` |
| `{"translations": [{"index": 0, "text": "..."}]}` | 校验失败并重试 |
| `{"translations": ["..."]}` | 校验失败并重试 |
| `{"translations": [{"index": 0, "text_en": "..."}]}` 但 index 集合不符 | 校验失败并重试 |

断言应覆盖 `llm.calls == 2`（默认外层一次重试）以及最终异常 trace 的来源，避免未来修改只保持 prompt 文本却破坏运行行为。

### 5.4 P2：prompt 与 JSON Schema 对“只允许这些键”的约束不完全一致

prompt 写明每个元素“只含 `index` 和 `text_en` 两个键”，但 `_TRANSLATION_SCHEMA` 当前只声明 `required`，没有明确设置 `additionalProperties: false`。JSON Schema 默认允许未声明的额外属性。

**影响：** 当前 `_validate_and_merge()` 会忽略额外字段，因此这不是本次形状漂移失败的直接原因；但 prompt 契约和 schema 契约并非完全一致。

**建议：** 在评估 mcode CLI 对 `additionalProperties: false` 的支持后，为顶层对象及数组元素补充该限制，并增加 schema 单测。如果 CLI 不稳定支持严格附加属性限制，则应将“只允许两个键”视为 prompt 约束，而在代码 validator 中显式检查未知键；两处不能长期保持模糊状态。

### 5.5 P2：诊断内容缺少数据保留与隐私策略

`trace.raw_head` 保存模型原始返回的前 4000 字符。字幕/封面标题可能含有用户提供的文本、项目名称或其他不宜长期留存的业务内容。

当前 `.gitignore` 已忽略 `outputs/`，可以降低运行产物误提交风险；但这不等于定义了本地访问控制和清理周期。

**建议：** 文档增加诊断数据说明：仅写入 job 输出目录、不提交 Git；对原始文本设截断和必要脱敏；明确诊断文件保留期限与人工导出要求；排障结束后按项目数据保留策略清理。不得把 API key、环境变量、完整 CLI 命令或账户凭据写入 trace。

### 5.6 P2：诊断文件名有秒级碰撞可能

`_dump_translation_failure()` 使用 UTC 秒级时间戳命名文件。如果同一输出目录在同一秒内发生并发失败，后写入可能覆盖先写入。

**建议：** 文件名加入微秒或短随机 ID，或使用原子创建/唯一命名机制；并在测试中验证两次快速失败会生成两个文件。

### 5.7 P2：本地验证数据尚不能独立复核

附件所述 32 个目标测试通过、全量 unit exit 0、mcode session 原始输出、console 事件编号和素材路径错误，都属于本机运行记录。本次审查确认了当前仓库有对应测试代码及修复实现，但没有获得 `.minimax` session、`console_run.log`、`console_run.json` 和该次本地 pytest 输出，因此不能独立重放这些事实。

**建议：** 后续验收归档至少包括：

- 命令行、执行时间、Python/依赖版本、Git SHA；
- pytest 完整摘要（用例数、通过数、失败数、退出码）；
- 真实 node_16a 的事件/状态摘要；
- 脱敏后的模型输出形状及 marker/SRT 检查结果；
- diagnostics JSON 样例，特别是 CLI 内部失败场景。

### 5.8 P3：HTTP 200 的表述需要说明观察层级

附件称四次响应均为 HTTP 200。仓库的 `McodeCLIClient` 通过本地子进程执行 `mcode exec`，仓库层可直接观察的是子进程返回、CLI envelope 和异常；它本身不直接暴露底层模型服务的 HTTP 状态码。

如 HTTP 200 来自 mcode session 的底层请求日志，应在文档中明确写成“模型服务请求返回 HTTP 200（依据本机 session 日志）”，不要与“mcode CLI 子进程 exit code 为 0”混用。

## 6. 推荐目标设计

### 6.1 翻译结构约束

保留三层约束，不引入候选键自动修复：

```text
Prompt 示例与明确字段规则
          ↓
CLI structured-output / JSON Schema 约束
          ↓
LLMTranslateClient._validate_and_merge() 业务契约校验
          ↓
成功后才写草稿、marker、SRT
```

三层职责：

- Prompt：告诉模型需要生成什么形状；
- CLI/schema：在可用时约束结构化输出；
- Python validator：对 index 集合、译文内容和时间码对齐进行最终业务校验。

### 6.2 失败 trace 结构

建议将诊断结构扩展为可审查、可测试的格式：

```json
{
  "node": "node_16a_translate_and_check",
  "translator_id": "mcode-cli",
  "prompt_version": "subtitle-translate-v2",
  "segments_count": 5,
  "fingerprint": "<sha256>",
  "error_code": "CLI_BACKEND_INVALID",
  "error": "<脱敏后的摘要>",
  "attempts": [
    {
      "outer_attempt": 1,
      "cli_attempt": 1,
      "status": "invalid_structured_output",
      "validation_error": "<校验错误>",
      "raw_head": "<截断后的模型输出>"
    }
  ]
}
```

说明：这是建议目标结构，不代表当前仓库已经实现。每次原始输出必须有长度上限；不记录凭据、环境变量和不必要的完整 payload。

### 6.3 失败语义

- 任一批次失败：整个翻译任务失败；
- 翻译失败：不写 marker，不把未翻译段写入英文状态；
- diagnostics 写入失败：不能覆盖原始翻译异常；
- resume：只有输入指纹、翻译器身份和 prompt 版本全部匹配时才复用 marker；
- 无源字幕：继续按当前产品约定 skip，不伪造空译文，也不将 skip 误报成真实翻译成功。

## 7. 分阶段执行计划

> 本计划将“已经合入的工作”与“建议补齐的工作”分开。执行前应先检查本机工作区和并行 worktree，避免覆盖其他会话 WIP；本计划不包含自动写文件、删除数据、启动/停止服务或推送代码等操作。

### 阶段 0：冻结审查基线与保存现场

**目标：** 明确要验证的代码版本、当前工作区状态和测试环境。

任务：

1. 在项目根目录执行 `git rev-parse HEAD`，记录实际 SHA；确认分支为 `main` 或明确记录所用修复分支。
2. 执行 `git status --short`，识别未提交修改、并行 WIP 和 worktree；不得将其他会话改动混入本次修复。
3. 确认运行时使用的翻译客户端确为 `LLMTranslateClient`，并记录 `translator_id`、CLI 后端、模型标识和 `max_attempts` 配置（不得记录密钥）。
4. 保存原始失败 run 的 `console_run.log`、`console_run.json` 和 mcode session 日志副本，确保日志脱敏且与 job ID 对应。

交付物：审查 SHA、工作区状态、运行环境摘要和脱敏日志索引。

**验收标准：** 能准确回答“当前运行代码是什么 SHA、是否有 WIP、实际外层/内层重试配置是多少”。

### 阶段 1：补齐 mcode CLI 失败 trace

**目标：** 让 CLI 内部重试失败时的 diagnostics 能提供每次尝试的有限诊断信息。

任务：

1. 为 CLI 内部每次尝试增加结构化记录：尝试编号、CLI 状态、schema/validator 错误、有限长度的原始输出摘要。
2. 通过专用异常属性传递 attempt records，避免只依赖拼接后的字符串异常信息。
3. 在 `chat_json_with_trace()` 异常分支提取专用异常的诊断属性；如果没有原始输出，明确标记 `raw_available=false`，不要把空字符串伪装成模型输出。
4. `node_16a` 继续只负责将翻译异常的 trace 落盘；不在此阶段重构全局 runner 或改变其他节点的错误语义。
5. 保持 `best-effort` 写盘：诊断失败不能覆盖 `TranslationError`。

建议涉及文件：

- `agent_gate/cli_client.py`
- `storyline_capabilities/vlm_client.py`
- `jy_common/translate_client.py`（仅在需要增强异常 trace 透传时）
- `tests/unit/` 下 CLI client 与翻译客户端测试

验收标准：

- 模拟 mcode 内部两次结构化输出失败，异常能携带两次尝试摘要；
- 外层 `TranslationError.trace` 可以读取该摘要；
- node_16a 诊断 JSON 保存该摘要；
- 日志不含密钥或完整敏感环境变量；
- 任一诊断写盘失败时，原始失败仍然抛出。

**目标：** 将事故中的输出形状漂移固化为可重复回归测试。

2. 验证每种错误结构最多执行一次外层重试，最终抛出 `TranslationError`。

| 风险 | 影响 | 控制措施 |
