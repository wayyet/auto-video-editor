# AI视频剪辑自动化工作流：环境确认与组件选型评估

> 本文档为《AI视频剪辑自动化工作流开发执行计划.md》的补充分析，聚焦两个问题：本地剪映版本是否满足要求、是否需要引入额外的第三方剪映自动化组件。结论已与执行计划第2节（架构总览）、第6.2节（加密防护与版本适配策略）交叉核对，不改变原计划的正式技术栈选型。

## 1. 剪映 V5.9 本地环境确认

**结论**：本地已安装剪映 Pro v5.9.0，满足执行计划第12节"第1周"任务与6.2节"策略甲"（全局版本锁定）的前提条件。

**版本选择依据**（基于官方仓库最新资料交叉验证）：

| 约束 | 说明 | 5.9.0 是否满足 |
|---|---|---|
| 明文读写 | 剪映自6.x起对 draft_content.json 加密，pyJianYingDraft 官方将功能支持范围划定在5.9及以下 | ✅ 是最后一个明文版本 |
| 自动导出 | 自动导出依赖旧版界面控件，7及以上版本通常已变更、不再满足 | ✅ 仍具备旧版控件 |

5.9.0 是"明文可读"与"自动导出控件仍存在"两个约束的交集，是当前唯一能同时满足读写与自动导出全部能力的版本，并非任意选定。

**待办提醒**：hosts 文件屏蔽剪映升级域名（阻断静默升级）这一步实操中容易遗漏，建议在第1周环境搭建验收清单中单独列一条检查项。

## 2. 第三方组件选型评估

评估对象：`capcut-cli`、`CapCutAPI`、`VectCutAPI`、`JianYing MCP Server`（hey-jian-wei/jianying-mcp）、`SmartCut MCP Server`（capcut-ai-editor）。

### 2.1 结论一览

| 组件 | 类型 | 与现有技术栈关系 | 建议 |
|---|---|---|---|
| capcut-cli | Node.js CLI，零依赖，直接读写草稿文件 | 功能与 pyJianYingDraft 重合；非 Python，与"变更④纯Python"决策有摩擦 | 不进正式技术栈，可选留作调试工具 |
| CapCutAPI | Python，HTTP API + 可选 MCP Server | 覆盖步骤5/8/9/11部分能力，不覆盖步骤7/10/13-17定制逻辑；独立进程增加心跳监控面 | 仅作接口设计参考，不整体替换 |
| VectCutAPI | Python，同 CapCutAPI 架构 + 云端渲染/预览 | 云端能力与"仅Windows本地"架构（变更③）无关；本地部分与 CapCutAPI 重复 | 不引入 |
| JianYing MCP Server | Python MCP服务，底层依赖 pyJianYingDraft | 与已选定底层库完全一致，可作技能层实现基座 | **建议评估采纳** |
| SmartCut MCP Server | Python MCP服务，口播类素材精剪专用 | 处理"原始长录制素材去停顿"，与17步流程"经OpenStoryline分镜规划后的素材"输入形态不匹配；原地写入无备份，与6.3节写入安全规范冲突 | 不引入 |

### 2.2 JianYing MCP Server 采纳前待核实清单

若决定评估采纳该组件用于替代部分自建 Skill 封装工作，落地前需确认以下三项：

1. **Python 版本兼容性**：该组件要求 Python 3.13+，需验证与 LangGraph 等现有依赖是否兼容。
2. **原子写入保护**：需在其接口外层补充执行计划6.3节要求的"临时文件写入 → 校验JSON合法性 → 原子重命名覆盖"，社区项目大概率未内置。
3. **中断前幂等设计**：需按5.2节坑③的要求，在其调用点补充幂等处理，不能假设其原生具备。

**建议定位**：可作为步骤5、8、9、10、11对应的"基础操作类"Skill 的实现基座，替代从零封装 pyJianYingDraft 的工作量；步骤7、13、14、15、16、17涉及的护栏校验、封面本地化、翻译与英文配音等业务定制逻辑，仍需团队自行扩展为独立的 MCP Tool。

CapCutAPI / VectCutAPI 的 MCP Tool 接口设计（create_draft / add_video / add_audio / add_text / add_effect / add_sticker 等命名与参数组织方式）可作为自建 Skill 接口设计时的参考样例，但不建议整体替换现有路线。
