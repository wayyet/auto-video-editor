## 1. 执行摘要

### 1.1 审查结论

本次修复的**总体技术方向正确**：在字幕进入剪映原生 `materials.texts[].content` 之前，根据画布宽度和字号插入显式换行；同时保留工作流状态中的原始字幕文本；既有草稿通过独立脚本回填。该设计比单纯依赖 `line_max_width` 更容易控制，也避免了直接改变时间轴切段、字幕时长和翻译状态。

但当前实现还不能视为完整验收。至少有三项 P1 问题需要先修复：

1. `safe_write_draft()` 在双文件写入中途抛异常时，不保证恢复快照，可能留下 `draft_content.json` 和 `draft_info.json` 不一致。
2. 剪映进程检测把“检测失败”当成“没有运行”，与脚本声称的 fail-closed（检测状态不明确时拒绝写入）不一致。
3. 脚本的折行自校验在 `safe_write_draft()` 返回成功后才执行；自校验失败只返回退出码 `2`，没有回滚已写入草稿。

此外，单元测试能证明文本算法和 JSON 结构，但不能证明剪映客户端实际将 `\\n` 按预期渲染为多行。原执行记录也明确把 `--apply` 和真机目检列为待完成事项。因此，**只有在安全写入问题修复、脚本测试补齐、剪映真机验证通过后，才能将本任务标记为完成**。

### 2.3 根因核验

以下结论得到当前代码支持：

1. `node_08_add_subtitles.py` 的 `_SENTENCE_BOUNDARY_RE` 主要按句末标点切分，长句如果没有这些句末边界，就可能保留为单条字幕。它不是按显示宽度切分。
2. `nodes/_subtitle_texts.py` 的原生素材字段包括 `line_max_width=0.82`，但 `force_apply_line_max_width=False`。这证明当前构造器没有启用强制行宽约束；“剪映实际如何处理该组合”仍属于客户端行为，需要真机验证。
3. 原生 `content` 的 `text` 字段在修复前直接使用传入文本，没有插入换行符。
4. `config.py` 当前设置画布为 `1080 × 1920`。构造器使用 `config.CANVAS_WIDTH` 作为折行计算宽度。
5. 英文字幕的翻译段仍按字幕段映射；翻译后字符数量可能明显增加，因此只按中文标点切分不足以保障英文渲染宽度。

原执行记录中的截图、两个草稿的真实 JSON、真机测量记录没有随本次读取的代码文件一并提供。本审查无法独立复核截图中 39 字和英文 157 字文本的原始测量，只能确认代码层面的根因链与报告描述一致。

## 3. 现有修复方案评估

### 3.1 值得保留的设计

| 设计 | 评价 | 原因 |
|---|---|---|
| 在 `make_text_material()` 统一折行 | 保留 | 中文、英文及已检查的开场标题素材共用入口，减少行为分叉 |
| 仅修改渲染文本，不改工作流原始字幕段 | 保留 | 避免把 UI 换行混入翻译源、时间轴切段和状态语义 |
| 使用显式 `\\n` 而不是依赖隐式自动折行 | 保留，但必须通过真机验证 | 行数和断点更可控，减少对剪映内部自动排版策略的依赖 |
| 保留 `alignment=1` | 保留 | 与逐行居中显示的目标一致；仍需实际客户端确认 |
| 已有换行不合并，重复执行保持幂等 | 保留 | 保护人工换行，并便于存量草稿重复执行 |
| 存量草稿默认 dry-run | 保留 | 默认不修改用户草稿，降低误操作风险 |
| 多 style 块跳过 | 保留 | 不应在不理解多样式 range 结构时盲目重排 |
| 写入前备份草稿目录 | 保留 | 能在受控异常路径下恢复用户草稿 |

### 3.2 需要修订的设计前提

#### A. 字符宽度公式只能作为估算，不能作为渲染保证

当前实现使用：

- `PX_PER_SIZE_UNIT = 6.4`
- `LINE_WIDTH_RATIO = 0.78`
- CJK 字符按 `1.0` 单位估算
- 普通半角字符按 `0.55` 单位估算
- 大写拉丁字符按 `0.67` 单位估算

其中 `6.4` 来自单一真机样本反推：字号 `6.25` 时全角字宽约 `40px`。这足以支撑第一版保守折行，但不能覆盖所有字体、粗体、字距、描边、特殊符号和混合文字。尤其英文字符 `W/M`、全大写文本、不同字体家族的实际宽度并不相同。

因此，`estimate_line_px()` 的通过只能表示“按当前估算模型没有超限”，不能等价于“剪映真实渲染绝不会裁剪”。文档中的“保证不超宽”“根治”等绝对表述应改为“按标定模型折行；最终由剪映客户端实测验收”。

#### B. 折行不等于重新分配字幕时间

当前方案只在一条字幕的渲染文本中插入换行，不会增加时间轴字幕段，也不会调整 `start_us`、`duration_us`。因此：

- 它解决的是单条字幕横向超宽问题。
- 它不解决单条字幕过长导致的阅读速度过快问题。
- 英文 157 字文本变为 4 行后，原时长不变；需要检查屏幕可读性和垂直占位。
- 不能把“每行不超宽”当成“字幕排版已合格”。

本阶段不建议自动拆分时间轴段，以免改变旁白同步和翻译段一一映射。应先增加行数、阅读速度和安全区域检查；如后续需要重新切段，另立设计变更。

#### C. 存量回填后的读取语义需要明确

`node_16_translate_subtitles.py` 的原生轨道读取路径通过 `text_display_text()` 读取原生 `content.text`。因此，存量脚本插入换行后，后续从原生草稿回读的文本可能包含这些 `\\n`；不能只根据 `text_en` 私有字段仍保留原文，就推断后续 SRT 一定仍是完全相同的字符串。

换行不会改变字幕文字本身，但可能改变 SRT 内部的换行格式。应增加回读和 SRT 测试，明确这是预期布局结果，而不是意外的数据变化。

## 5. 修订后的目标设计

### 5.1 设计目标

- 新生成的中文字幕、英文字幕和开场标题都经过统一排版处理。
- 超宽字幕按实际画布宽度和有效字号折行，尽量在自然语义边界断行。
- 工作流原始字幕文本、翻译源、字幕段时间和旁白同步关系不因视觉折行而改变。
- 存量草稿支持 dry-run、备份、可验证写入、失败回滚和幂等重复执行。
- 不覆盖用户手工添加的其他文本素材、轨道或多样式文本。
- 所有自动校验必须明确区分“估算通过”和“剪映实际渲染验收通过”。

### 5.2 新草稿生成设计

**保持共用构造入口：**`nodes/_subtitle_texts.py::make_text_material()`。

建议处理顺序：

1. 调用方传入原始字幕文本和最终生效的 style。
2. 获取目标草稿实际画布宽度。当前项目配置是 `1080 × 1920`；如以后支持多画布，应从草稿配置传入，不能无条件假定所有草稿均为 1080 宽。
3. 根据字号、字体信息、粗体/字距等条件计算可用行宽。第一阶段可以继续使用当前经验模型，但必须标注模型版本和估算属性。
4. 在合法断点处插入 `\\n`。中英文分别制定断行策略；不能为了填满宽度拆开英文单词。
5. 将折行后的渲染文本写入原生 `content.text`，`styles[0].range` 与最终文本长度保持一致。
6. 私有字段仍保留调用方提供的原始文本，state 中的 `subtitle_segments_zh/en` 不改写。
7. 记录布局结果：原始字符数、折行后行数、估算最宽行、使用的字号和布局模型版本。日志不输出密钥或完整敏感路径。

**重要约束：**折行算法不得改变时间段、字幕顺序、`material_id`、text 轨道引用、字体/颜色/描边/位置和动画绑定。

### 5.3 存量草稿回填设计

继续使用独立脚本 `scripts/fix_draft_subtitle_wrap.py`，但将执行过程明确拆成四步：

1. **Preflight：**校验所有 `--draft-dir`、`draft_content.json`、`canvas_config.width`、素材格式和剪映进程状态；多目录全部预检成功前，不得开始写入。
2. **Plan：**只在内存中生成修改计划，报告每条素材的旧文本、新文本、字号、估算最宽行、跳过原因；默认 dry-run 不落盘。
3. **Apply：**为每份草稿创建快照；执行受保护的双文件写入；任何写入异常、双文件不一致或布局自校验失败，都必须恢复该事务对应的快照。
4. **Verify：**重新读取磁盘文件，检查 JSON 可解析、`draft_content.json` 与 `draft_info.json` 一致、目标文本 range 正确、每一行符合估算预算、其他素材与轨道未变化。随后进行幂等复跑和剪映客户端目检。

多目录执行策略需要明确：推荐第一版先保证**单份草稿事务完整**，同时在报告中明确多目录之间不是整体原子事务；如果中英文两个草稿必须保持成对一致，再增加跨草稿协调提交和失败整体回滚，不应隐含承诺。

### 5.4 写入安全设计

建议让 `safe_write_draft()` 成为唯一的事务边界：

```text
检测进程状态
    ├── RUNNING  → 拒绝写入
    ├── UNKNOWN  → 拒绝写入
    └── NOT_RUNNING
           ↓
      创建整目录快照
           ↓
      写入 draft_content.json
           ↓
      写入 draft_info.json
           ↓
      双文件一致性验证
           ↓
      字幕布局验证
       ├── 通过 → 提交成功
       └── 失败 / 任意写入异常
                ↓
             恢复快照
                ↓
             校验恢复结果
                ↓
             返回失败（包含原始异常和恢复结果）
```

注意：两个 `os.replace()` 各自是单文件原子替换，不代表两文件组成了一个真正的原子事务。必须由上层捕获第二次写入失败并恢复快照，或采用可回滚的成对提交实现。

进程检测建议使用三态结果：

- `RUNNING`：确认剪映进程在运行，拒绝写入。
- `NOT_RUNNING`：确认剪映进程不存在，允许继续。
- `UNKNOWN`：命令失败、超时、权限不足、平台不支持或结果无法判定，拒绝写入。

仅仅连续检查两次仍不能完全消除检查后剪映马上启动的竞态。因此日志应准确称为“进程状态门禁”，不要在没有系统级互斥机制时声称获得绝对排他锁。

### 7.2 必须覆盖的关键用例

| 类别 | 输入/故障注入 | 验收结果 |
|---|---|---|
| 中文长句 | 39 字真实 cue | 插入换行；字符顺序不变；每行估算宽度不超预算 |
| 英文长句 | 157 字真实 cue | 按英文词边界折行；不拆普通英文单词；重组文本不丢词 |
| 已有换行 | 输入含一个或多个 `\\n` | 不合并已有行；再次执行结果不变 |
| 标点 | 闭合标点、开口括号、中英文逗号 | 不把闭合标点放到行首，不把开口标点悬在行尾 |
| 混合文本 | 中文、英文、数字、大小写、标点混排 | 不丢字符；宽度估算可追溯 |
| 多样式 content | `styles` 多于一个 | 跳过并列出原因，不擅自改 range |
| 空文本/坏 JSON | 空字符串、非 JSON、结构缺失 | 安全跳过；准确统计原因；不修改文件 |
| 双文件写入异常 | 第二个文件 `os.replace()` 抛异常 | 自动恢复快照；两个文件恢复一致 |
| 进程检测异常 | `tasklist`/`pgrep` 超时或失败 | 返回 `UNKNOWN` 并拒绝 apply |
| 布局自校验失败 | 注入超宽行 | apply 失败并回滚，不留下已修改草稿 |
| 幂等 | 同一草稿执行两次 | 第二次 `changed=0`；草稿内容不发生变化 |
| 回读/SRT | 回填后从 native text track 读取 | 文本和时间不丢；换行输出符合约定 |

## 8. 推荐执行顺序与优先级

推荐顺序：

1. **先修 P1-01、P1-02、P1-03**：确保任何写入异常和任何无法确认的剪映进程状态都不会留下半成品草稿。
2. **再完成 P1-04、P1-05、P1-06**：为存量回填脚本补齐可自动回归的行为和失败路径。
3. **执行 P0 样本与全仓库入口审计**：确保本次设计覆盖全部自动字幕写入路径。
4. **处理 P2 算法与可读性项**：先补足估算边界和文本无损性，再决定是否增加自动时间轴切段。
5. **执行 P3 真机验收**：最后在剪映客户端确认真实渲染、动画与画面安全区域。
6. **完成 P4 文档回填和发布**。

不建议在 P1 安全问题未修复前，对正式用户草稿执行 `--apply`。当前实现的折行方向可以保留，但存量回填的写入事务、进程检测和真机渲染验收仍需补齐。
