# 生成视频全画面模糊根因分析（console-64da836e2f3f）

> 日期：2026-11-11　|　状态：**仅分析，修复未执行**　|　分析对象：Thread ID `console-64da836e2f3f`
> 导出成片：`outputs/AutoVideo_console-64da836e2f3f.mp4`（41,039,927 字节，约 34.78 秒，按大小/时长推算码率约 9.4 Mbps）

---

## 1. 问题现象

用户从剪映导出成片后反馈：**生成的视频画面全部模糊，与原始视频差别很大**。原始素材在播放器里清晰锐利，成片方向正常（竖屏、内容不歪斜），但整片清晰度显著下降。

## 2. 结论速览

- **模糊主因**：管线全程无视素材的**旋转元数据**（rotation metadata，即视频文件里记录"拍摄时手机竖握、存储时横着存、播放时转 90°"的标记），把竖屏视频当成 1920×1080 横屏写进了剪映草稿的素材声明。剪映按声明尺寸做布局，把"横屏素材"铺满 1080×1920 竖屏画布时放大约 1.78 倍再裁切，实际像素却是竖屏的——于是**方向正确但全画面放大模糊**。
- **副发现 1（封面）**：`node_14` 生成的封面图是"深色底 + 巨大 JSON 文本"，原因是从视频抽帧的输入图全流水线无人生产 + 字幕 JSON 字符串被直接当标题绘制。
- **副发现 2（节奏）**：时间轴第 2 段把 0001.mov 最后 **0.883 秒**拉长到 **11.593 秒**（约 13 倍慢放感），且草稿 speed 字段写 1.0，与源/目标时长比自相矛盾；三层本应拦截的护栏全部失效。

## 3. 基础事实：素材真实参数

来源：管线自己的 ffprobe 完整探测产物 `outputs/console-64da836e2f3f/assembly/media.json`（本分析中 ffprobe/Python 直接探测被环境拦截，故以该产物为权威，内容与 PyAV 探测 `storyline/load_media.json` 一致）。

| 属性 | 0001.mov（media_0001） | 0002.mov（media_0002） |
|---|---|---|
| 容器/编码 | MOV / HEVC(H.265) Main 10 | MOV / HEVC Main 10 |
| coded 尺寸¹ | 1920×1080 | 1920×1080 |
| Display Matrix 旋转² | **-90°** | **-90°** |
| 实际显示尺寸 | **1080×1920（竖屏）** | **1080×1920（竖屏）** |
| HDR 特性 | 杜比视界 Profile 8.4 + HLG³、BT.2020、10bit | 同左 |
| 帧率/时长/码率 | 25fps / 30.883s / ~7.2 Mbps | 30fps / 27.935s / ~8.6 Mbps |
| 音频 | AAC 44.1kHz 立体声 | 同左 |

> ¹ **coded 尺寸**：文件里像素实际存储的宽高。iPhone 竖拍视频约定俗成"横着存 + 旋转标记"。
> ² **Display Matrix（显示矩阵）**：MP4/MOV 里的一块元数据，告诉播放器"把这帧转多少度再看"。
> ³ **HLG**（Hybrid Log-Gamma，arib-std-b67）：一种 HDR 传输曲线；**杜比视界 8.4** 是兼容 HLG 的单层 DV 格式。

管线自己的 `technical_risks` 都已警告：`"HDR transfer detected (arib-std-b67); SDR preview may need tonemapping"` 与 `"rotation metadata present: -90"`——信息在，但下游没消费。

原始像素质量实证：`.video_agent/video_frames/0001_ca98d8ee_full/sheets/` 下的抽帧拼贴图（ffmpeg 按 2fps 抽样）显示画面**正立、清晰**——ffmpeg 解码时默认应用旋转，说明源没问题。

## 4. 模糊根因链（四步）

1. **探测环节无视旋转**
   `video_edit_capabilities/render.py:92-120` `probe_video_size()` 只执行
   `ffprobe -show_entries stream=width,height`，读到的永远是 coded 尺寸 1920×1080。
   `storyline/load_media.py` 的 PyAV 元数据同样只报 coded 尺寸。

2. **草稿把素材声明成横屏**
   `storyline/native_draft.py:160-173` `_probe_size()` 复用上述探测；`:192,241` 把
   `width: 1920, height: 1080` 写进 `materials.videos[]`（本任务 `drafts/draft_content.json` 三个素材条目均如此）。
   而画布是竖屏 1080×1920（`config.py:121-123` CANVAS 常量）。

3. **剪映按声明尺寸做布局 → 放大 1.78 倍再裁切**
   剪映 5.9 渲染器以素材声明的宽高为布局基准：一个"1920×1080 横屏素材"要铺满 1080×1920 画布，
   需按 `max(1080/1920, 1920/1080) = 1.78` 倍放大并裁掉超宽部分；但它解码出的实际像素经旋转后是
   1080×1920 竖屏——于是竖屏像素被放大裁切，**方向对、满幅、但糊**。
   （此机制为高置信推断，修复计划中安排了 2 分钟 A/B 实验做最终确证，见 §9。）

4. **历史绕过方案在主链路上悄悄失效**
   `nodes/node_05_generate_draft.py:332-336` 的注释表明开发者早已观察到"比例不符的素材由剪映直接拉伸"，
   并为此做了**预裁切归一化**（把源文件居中裁成 9:16 再给草稿引用）来绕过。但 storyline 主链路的草稿
   **引用的是 `inputs\` 原始素材，而不是 `normalized_sources\` 里的归一化文件**——这是代码注释自认的
   已知限制 R3（`node_05:96-105`：canonical 路径只归一化第一个视频、且归一化产物不进 materials，仅写进
   `state.draft_source_normalized_path`）。实测本任务及另外 3 个历史任务的 `draft_content.json`
   materials 全部指向 `inputs\*.mov`，无一引用归一化文件。

## 6. 为什么"看着方向是对的"反而说明问题在声明尺寸

若剪映完全无视旋转元数据，画面应整体横躺；若剪映完全自探测文件，声明值无关紧要，画面应清晰 1:1。
实际是"**方向正 + 全画面糊**"——恰好对应"旋转被解码器应用了（像素正了），但布局按声明的横屏尺寸算了
（放大 1.78 倍裁切了）"。这一组合只有"声明尺寸驱动布局"能同时解释，也与 E6（剪映不纠正声明值）一致。

## 7. 副发现 1：封面全是"深色底 + JSON 文本"

现象：剪映草稿目录 `covers/cover_9x16_zh.png` 等 6 张（9:16/16:9/4:3 × zh/en）全部是 #14141C 纯色底，
上面画着白色描边的巨大文字，内容是 JSON 片段（如 `rue", "italic": false`）。

根因（两点叠加）：

1. **输入帧图永远缺失**：封面渲染期望草稿目录存在 `cover_source_frame.jpg`（从视频抽的一帧），
   但全仓库 grep 该文件名只有消费者（`nodes/node_14_make_covers.py:64`、`mcp_clients/jianying_cover_client.py:110`）
   和单测自造图，**没有任何节点生产它**。缺图时代码回退纯色占位
   （`node_14_make_covers.py:72-73` 的 `Image.new("RGB", (1080,1920), color=(20,20,28))`）。
2. **字幕 JSON 被当标题绘制**：node_08 写字幕时 content 是原生 JSON 字符串
   （`nodes/_subtitle_texts.py:55` → `jy_common/native_text.py:32-59` 构造，形如
   `{"styles":[...,"bold":true,"italic":false,...],"text":"…"}`）。而标题读取处
   `node_14_make_covers.py:148-159` 直接 `str(texts[0]["content"])` 把整段 JSON 当文字画上去
   （`node_15_localize_covers_en.py:37-42` 同病）。仓库现成的
   `jy_common/native_text.py:84-89 text_display_text()`（原生 JSON 优先取 `text` 字段）没被用上。

## 8. 副发现 2：0.883 秒素材被铺满 11.593 秒

本任务素材总长 58.8s 压到 35s。最终草稿三段各占 11.593s，但源窗口分别是
`0001.mov[0→30s]`、`0001.mov[30→30.883s]`、`0002.mov[0→27.935s]`——第 2 段只有 0.883 秒素材却铺 11.593 秒。
四层失守：

1. **30 秒强切产生残尾**：`storyline_capabilities/split_shots.py:34` `DEFAULT_MAX_SHOT_MS=30000`，
   `_clips_from_cuts`（`:229-253`）把 30.883s 的镜头切成 `[0,30000]` + 残尾 `[30000,30883]`；残尾未被任何环节丢弃。
2. **TTS 失败改走卡点均分**：本任务 FireRed TTS（:8010）不可达（既有环境问题）→ `timeline_planner.py:94-96`
   `has_tts=False` → `beat_align` 路径；`_distribute_by_beats`（`:209-241`）把 35000ms 对齐到 BGM 节拍
   470ms 的整数倍得 34780ms，再 **÷3 均分**（每段 11593ms）——分配与各段源跨度完全解耦。
3. **mapper 硬编码 speed=1.0**：`storyline/mapper.py:161` 固定写 `"speed": 1.0`，
   不做 `源跨度/目标跨度` 换算；计划产物（`storyline/timeline_plan.json`）的 Clip 契约本就无 speed 字段
   （`storyline/contract.py:67-100`），0.883s 源配 11.593s 时间轴能过校验（`:213-235`）。
4. **node_07 护栏早退**：`nodes/node_07_speed_fit.py:103-109` 只累加 target 时长，
   34.78s ≤ 35s 直接整体跳过；即使运行，其速度公式（`:111-121`）也从不读 `source_timerange`。
   `qa_gate`（`nodes/storyline/qa_gate.py:93-102`）只查总时长阈值，同样放行。

## 10. 其他观察（不计入本次修复）

- **HDR 色差属预期**：源是 HLG/DV，导出 SDR 会有色调映射差异（偏灰/偏亮），这是色彩管理问题，不是模糊；
  如需"所见即所得"色彩，后续可评估预转码 SDR。
