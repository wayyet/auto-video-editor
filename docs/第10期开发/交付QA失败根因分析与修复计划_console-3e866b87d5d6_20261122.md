### 第二层失败的确凿回执(zh spec sidecar 的 `compile.last_result`)

```json
"status": "failed_blocked_features",
"note": "UnsupportedManualFeatureError('spec 携带 SDK 无法忠实重建的人工高级特征,
        已暂停编译并保留原草稿:[{\"kind\": \"manual_text_track\", \"count\": 1,
        \"segment_ids\": [\"hook-title-seg-1\"]}]')"
```

机制:

- 提取器 `jianying_sdk/timeline_extractor.py:483-494`:文本轨上「不在 spec 字幕计划内」(既不匹配 spec 字幕 id/文本,也不匹配我方字幕 material 前缀)的段 → 判 `manual_text_track`,写入 `spec.timeline.blocked_features`;
- 编译器 `jianying_sdk/compiler.py:547-551`:`blocked_features` 非空 → 抛 `UnsupportedManualFeatureError`,fail-closed 保留原草稿——设计意图是防止编译把**人工在剪映里做的编辑**覆盖丢失;
- 而 `hook-title-seg-1` 是 node_09b 自己写的开场标题(`nodes/node_09b_inject_opening_hook.py:245`,`id_prefix="hook-title-seg"`),**被我方流水线写进去的内容误判成了人工内容**。

### node_11 首编「发布前失败」的推理链

1. 审计文件里**完全没有** `node_11_compile_zh` / `node_11_compile_en` 记录;
2. `write_draft`(`nodes/_draft_io.py:217`)即使发布失败也会追加 `status:"failed"` 审计记录 → 说明**根本没走到发布**;
3. 快照佐证:zh 草稿 `.snapshots` 在 03:29:45(post-node_07)与 03:30:34(post-node_09b)之间没有任何编译写入痕迹;
4. 推论:失败发生在 `compile_spec`(或其前置的提取/指纹步骤),异常被 `jianying_sdk/pipeline.py:99-114` catch 后以 record 返回,node_11 侧记入 `status_log`(`node_11_compile_zh:<状态>`)与 `error_log`(`[node_11] SDK 编译失败(zh),草稿保留编译前快照: <异常repr>`)——**只存在于运行状态(PG checkpoint/事件),磁盘上的回执被修复期重编译覆盖**。

### 对照实验:英文分支为什么没事

同一次 repair 对英文分支草稿(无 hook 文本段)的重编译**成功**:

- 审计节点 `delivery_qa_recompile_en`(19:30:37 UTC):`materials.texts 0→6`、`transitions 0→3`、`effects 0→6`、`material_animations 0→6`、`video_effects 1→2`、`track_segments 6→12`,花字指纹 effects_sha 非空;
- 重编译后 en sha=`960b507d7c15bdb7c326200936badc3f28b2950e7addeb592effc31c15513ed7`,正是截图 QA 报告里 en 的哈希——证明**编译管线本身是好的、spec 内容可编译**;
- 代价:该成功编译把 en 稿 node_09b 写入的 `hook-effect-1` **静默抹掉了**(SDK 全量重建,hook 不在 spec;video_effects 前后 1→2,剩下的是 spec 的两个辉光特效)。QA 没拦是因为 video_effects 恒可选、不进 required 闸门。这验证了 `graph.py:685` 注释「白名单放行又会被 SDK 重建静默丢弃」的预言——**修复必须「豁免 + 编译后重放 hook」配套**。

### 一个反直觉事实

repair 分派表(`nodes/node_delivery_qa_repair.py:101-106`)里 `subtitles_zh` 属"数据性缺失、不可自动修复",但 repair 的 `transitions` 动作触发的是**全量 spec 重编译**——编译成功会连带把 spec 里的 6 条中文字幕一起写回。**也就是说:只要第二层(hook 阻断)修掉,本次任务的复检本可以通过。**

## 三、结构性缺口(设计层面)

1. **repair 期重编译必撞 hook**:hook 已特意移到 node_11 之后(`graph.py:684-689`,2026-11-22 修复),保护了首编;但 QA repair 的重编译(`node_delivery_qa_repair.py:41-75`)发生在 node_09b 之后——今后每次走到「repair 需重编译转场/字幕动画」的路径,必然被 manual_text_track 阻断,永远修不好。
2. **repair 编译回执被静默吞掉**:`_recompile_drafts` 对 `compile_and_publish_draft` 的返回 record 不做任何检查、不写 error_log/status_log(编译失败只留在 spec sidecar 里),排障时完全不可见。
3. **hook 不在 spec 内,任何编译成功都会抹掉它**(本次 en 稿已实际发生):需要「编译后重放 hook」或后续把 hook 改造成 spec 构建段。
