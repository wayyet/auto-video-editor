# AI视频剪辑工作流编排设计——通俗讲解

## 📌 一句话概括

> 这篇 RFC 讨论的核心问题是：**我们已经有了一套 17 步的 AI 视频剪辑流程，现在要把它从"人坐在电脑前一步步点"升级为"系统自动跑、人只在关键节点介入"的自动化流水线。**

---

## 一、先搞懂背景：这 17 步到底在干嘛？

想象你是一个短视频创作者，手里有一段旅行素材（比如"吉隆坡武吉免登"），你要把它做成一条精致的短视频，还要出中英文两个版本。

整个流程可以分成 **四大阶段**：

| 阶段 | 做什么 | 对应步骤 |
|------|--------|----------|
| 🧹 准备 | 清理缓存、启动工具 | 步骤 1-4 |
| 🎬 粗剪 | 导入剪映、人工排序、变速适配 | 步骤 5-7 |
| ✨ 精修 | 加字幕、转场、特效、花字、贴纸、BGM、封面 | 步骤 8-15 |
| 🌍 英文化 | 翻译字幕、AI 配音 | 步骤 16-17 |

**关键认知**：这 17 步目前已经被拆成了独立的"技能"（skill），每个 skill 做一件事。但问题是——**它们之间怎么串起来、谁先谁后、哪里要等人、哪里能并行**，这些"编排"逻辑还藏在人的脑子里，没有系统化。

---

## 二、这篇 RFC 要解决什么问题？

用大白话说，就是四件事：

### 1. 把"隐藏的依赖"摆到台面上

表面上看 17 步是一条直线（1→2→3→...→17），但实际上：

- **有分叉**：步骤 7 做完变速后，要复制一份"纯视频"草稿给英文分支用。这个"复制"动作在原来的 17 步里根本没写出来，全靠默契。
- **有并行**：英文分支（步骤 16-17）和中文精修（步骤 8-14）其实可以同时跑，不用互相等。
- **有人工关卡**：步骤 6（人工调顺序）和步骤 12（人工选 BGM）必须等人操作，系统不能跳过。

> 🎯 **类比**：就像做菜，你以为是一道一道按顺序做，但其实"炖汤"和"炒菜"可以同时开火，而且"尝味道"这一步必须等厨师本人来。

### 2. 分清哪些步骤能自动化，哪些必须走 GUI

这是一个很实际的约束：

| 类型 | 说明 | 举例 |
|------|------|------|
| ✅ 可以直接改文件 | 剪映的草稿本质是一个 JSON 文件（`draft_content.json`），用 Python 库 `pyJianYingDraft` 直接读写就行 | 加字幕、变速、导入草稿 |
| ⚠️ 必须走剪映 GUI | 涉及 VIP 付费素材（花字、贴纸、转场等），这些资源 ID 需要剪映客户端用你的账号去云端验证，你没法伪造 | 转场特效、花字动画、贴纸 |
| 🖥️ 必须 Windows | 剪映的导出功能和部分 VIP 操作只在 Windows 客户端支持 | 最终导出成片 |

> 🎯 **类比**：就像你可以通过 API 直接操作数据库（改文件），但有些功能必须打开管理后台点按钮（走 GUI），而且这个后台只有 Windows 版。

### 3. 选一个能"等得起"的执行引擎

人工关卡的等待时间是不确定的——调个顺序可能 5 分钟，选个 BGM 可能拖好几天。普通的任务调度器（比如 Airflow）遇到这种情况会很尴尬：任务挂在那里占资源，或者超时被杀掉。

### 4. 让失败可以回滚、可以审计

每一步做完都要有"存档点"，出了问题能回到上一个好的状态，而不是从头再来。

## 三、编排执行计划：怎么跑？

整个流程画成图是这样的：

```
清理缓存 → 生成分镜 → 导入剪映 → 【人工排序】→ 变速适配
                                                    ↓
                                          ┌─────────┴─────────┐
                                          ↓                   ↓
                                    中文主线精修          英文分支（并行）
                                    字幕→特效→花字→      翻译字幕→AI配音
                                    贴纸→BGM→音量→封面
                                          ↓                   ↓
                                          └─────────┬─────────┘
                                                    ↓
                                              交付打包
```

**核心优化点**：步骤 7 做完变速后，立刻复制一份草稿给英文分支。这样中文那边做转场、贴纸、BGM 的时候，英文那边可以同时在翻译字幕和生成配音，**两条线互不干扰，并行执行**。

## 四、技术选型：为什么选这些？

### 4.1 编排引擎：Temporal

**Temporal 是什么？** 简单说，它是一个"工作流引擎"，你用它写代码来定义"先做什么、再做什么、哪里等、哪里并行"。

**为什么不用其他方案？**

| 方案 | 为什么不选 |
|------|-----------|
| **LangGraph** | 它是给"LLM 调用链"设计的，但我们这条流水线大部分步骤是文件操作和 GUI 自动化，LLM 只是其中几步。硬塞进去是逆着框架设计意图走。 |
| **n8n / Dify** | 简单 API 编排很好用，但遇到复杂分支、多语言 worker（Python + .NET）、代码级测试就比较吃力。 |
| **Airflow / Prefect** | 更适合数据管道（定时跑批），不太擅长"等人工操作好几天"这种场景。 |

**Temporal 的三个杀手锏**：

1. **Signal 机制**：工作流可以"暂停"等人工操作，人做完了发一个信号（Signal），流程继续跑。暂停期间不占任何计算资源，等几天都没问题。
2. **Task Queue 路由**：可以把任务分发到不同的 worker 池。比如"需要 Windows 的任务"发到 Windows 机器，"普通任务"发到 Linux 容器。
3. **持久化执行**：每一步的状态都会持久化保存，进程崩了重启后能从断点继续，不用从头来。

> 🎯 **类比**：Temporal 就像一个超级项目经理，它记得每个任务做到哪了、谁还没交活、哪些任务可以同时派给不同的人干。

### 4.2 技能执行层：AI 决策和机械执行要分开

这是一个很重要的架构思想。每个 skill 拆成两半：

```
┌─────────────────────────────────────────────┐
│  AI 决策层（LLM）                            │
│  输入：视频内容、上下文                        │
│  输出：结构化 JSON 决策                       │
│  例如："00:03-00:07 插入推近转场，花字用XX样式"  │
└──────────────────┬──────────────────────────┘
                   ↓ JSON
┌─────────────────────────────────────────────┐
│  机械执行层（纯代码）                         │
│  输入：上面的 JSON 决策                       │
│  输出：修改 draft_content.json / 驱动 GUI     │
└─────────────────────────────────────────────┘
```

**为什么要这样拆？**

- **AI 部分**可以单独换模型、调 prompt，不影响文件操作代码
- **机械部分**可以脱离 LLM 单独写单元测试，不用每次都花钱调 AI
- **天然有审计轨迹**：AI 决策了什么、实际写了什么，是两条分开可查的记录

> 🎯 **类比**：就像建筑设计（AI 决策）和施工（机械执行）分开。设计师换了不影响施工队，施工队可以单独验收，而且设计图纸和施工记录分开存档。

### 4.3 剪映操作层：能改文件就不开 GUI

优先级：**直接改 JSON 文件 > 控件树自动化 > 视觉坐标点击**

- `pyJianYingDraft` 这个 Python 库可以直接读写剪映的草稿文件，速度快、可测试
- 但 VIP 素材（花字、贴纸等）必须走 GUI，因为需要剪映客户端用你的账号去云端拉资源
- 走 GUI 时，优先用控件树自动化（类似 Selenium 操作网页），实在不行再用截图+坐标点击

⚠️ **注意风控**：剪映是消费级 App，高频、固定节奏的自动点击可能触发风控。建议 GUI 操作之间加随机延时。

### 4.4 人工介入层：从"对话暂停"到"IM 通知"

| 阶段 | 方式 | 说明 |
|------|------|------|
| 现在 | 对话轮次 | 在 Claude Code 里跑，做到人工关卡就停下来等你说话 |
| 规模化 | IM 机器人 + Webhook | 企业微信/飞书推送预览，人点按钮确认，Webhook 通知 Temporal 继续 |

### 4.5 版本管理：用 Git 做快照

每个关键节点对草稿目录做一次 `git commit`，免费获得：
- **回滚能力**：出了问题 `git checkout` 回去
- **Diff 能力**：看看每一步到底改了什么
- **分叉能力**：英文分支的"复制草稿"就是一次分支操作

## 五、风险清单：有哪些坑？

| 风险 | 通俗解释 | 怎么应对 |
|------|---------|---------|
| 步骤 13 没有对应的 skill | 调整音量这步没人写自动化脚本，流程会卡住 | 补一个 skill |
| 分叉时机没写明 | "什么时候复制纯视频草稿"全靠默契，容易被改坏 | 显式加一个"步骤 7.5" |
| 剪映风控 | 自动化点击太规律可能被当成机器人 | 加随机延时 |
| Windows 限制 | 导出和部分 VIP 操作只能在 Windows 上跑 | 单独维护 Windows worker 池 |
| 英文封面范围没定义 | 如果以后要英文横版封面，现在没规划 | 提前补一条本地生成分支 |

## 六、落地建议：分三步走

这是最务实的部分，**不要一上来就搭 Temporal**：

### 🥇 第一步：先跑通（现在）

> 什么都不改，就用 Claude Code 按顺序把 17 个 skill 手动跑一遍。人工关卡就是对话暂停。

**为什么？** 因为这套 skill 本来就是为这种模式设计的。先跑通一遍，你才能知道每步实际耗时多少、哪里真的会卡、哪些假设是错的。

### 🥈 第二步：解耦（接下来）

> 把机械性的 skill（JSON 读写、变速计算、封面生成）抽成独立的、有单元测试的脚本/CLI。

**为什么？** 把"要不要调 LLM"和"文件怎么改"分开，调试和复用都方便。

### 🥉 第三步：规模化（产出多条视频时）

> 包进 Temporal，人工关卡换成 IM + Signal，用 OpenStoryline 的 Skill Archiving 复用剪辑风格。

**为什么？** 这时候才真正称得上是一条"数字员工"视频生产线。

## 八、给中级开发者的行动建议

1. **先理解剪映草稿的文件结构**：去翻 `pyJianYingDraft` 的文档和源码，搞懂 `draft_content.json` 长什么样，这是整个系统的"数据层"。
2. **先跑通再优化**：不要一上来就搭 Temporal，先用最简单的方式把 17 步串起来跑一遍。
3. **关注"AI 决策 vs 机械执行"的分离**：这是整个架构里最值得学习的设计思想，不管用不用 Temporal，这个拆法都适用。
4. **留意 Windows 约束**：如果你的开发环境是 Mac/Linux，要提前规划 Windows 测试环境。
5. **读一读 Temporal 的 Python SDK 文档**：重点看 Workflow、Activity、Signal 这三个概念，10 分钟就能理解核心模型。
